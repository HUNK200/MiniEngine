  ```
  no case in suite 'Nope' (35 case(s) registered)
  ```

  `tests/test_main.cpp:98` 就是 `return 1`，旁边那句注释写着
  "否则 CTest 会报 `100% tests passed`，属于假绿"。
  ⚠️ 所以"命令报失败"在这里是**门闩在正常工作**，不是程序出错。

### B1 `Time::LimitFPS` 的自动化守卫 ⭐ 最高价值

- **现状**：`tests/test_time.cpp` 里 `PlatformWaitBeatsSleepGranularity` 测的是
  `platform::Wait()` **本身**；而 `LimitFPS()` 的**组合逻辑**
  （用哪些边界算 `remain` 与 `spin`、早退条件、`BeginFrame` 与 `LimitFPS` 共享
  同一个 `m_begin`）只被**肉眼看过**（"FPS 稳定在 58~61"）。
- **为什么算债**：**步骤 1 那个 bug 正是这里漏掉的**——当时的 `LimitFPS` 用
  `sleep_for`，`platform::Wait` 的用例根本照不到它，是靠"跑 exe 看 FPS 抖"才发现的。
  也就是说：**就算把 `LimitFPS` 改回 `sleep_for`，现在 34 个用例全绿**。
  这是本项目到目前为止最值得补的一条守卫。
- **做法**：在 `tests/test_time.cpp` 加 1 个用例（`Time` suite 从 8 → 9）。
- **⚠️ 执行时发现的坑：原设计"单帧测 60fps"**根本测不出来**，必须换采样点**：

  `LimitFPS` 是先 `Wait(remain - spin)` 再自旋，`spin = min(2ms, target/4)`。
  换成 `sleep_for` 之后实际睡多久，取决于**请求值落在 15.625ms tick 网格的哪一侧**：

  | 采样点 | 请求的睡眠 | `sleep_for` 版实际睡 | 帧时间 | 抓得住吗 |
  | --- | --- | --- | --- | --- |
  | **60fps** | 14.667ms | `Sleep(15)` → 15ms **不到** tick → 一跳 15.6ms | 自旋补到 16.7ms → **正常** | ❌ **抓不住** |
  | **56fps** | 15.857ms | `Sleep(16)` → 16ms **越过** tick → 两跳 **31.25ms** | 31.25ms | ✅ **确定性抓住** |

  所以最终写成**两个采样点**：60fps（真实用的那个，界 `[16ms, 25ms]`）
  + **56fps**（`[17ms, 25ms]`）—— 56 是**故意挑在 tick 另一侧**，
  把"有时发生"变成"每次都发生"，这才是这条用例站得住的理由。

- **验收**：
  ```powershell
  cmake --build build --config Debug
  .\build\bin\Debug\mini_tests.exe Time     # 期望 9 passed（现在 8）
  .\build\bin\Debug\mini_tests.exe          # 期望 35 passed（现在 34）
  # 连跑 10 次确认上界不抖（上界就是怕这个）
  1..10 | % { .\build\bin\Debug\mini_tests.exe Time | Select-Object -Last 1 }
  ```
- **反向验证（这条是 B1 的验收关键，**不是可选项**）**：
  把 `engine/src/core/Time.cpp:95` 的 `platform::Wait(...)` 换成
  `std::this_thread::sleep_for(...)` → **`LimitFpsAchievesTargetFrameTime` 必须变红**。
  如果它**没红**，说明界选错了，这条守卫等于不存在 —— 把实测帧时间报回来重新定界。
  改完还原：`git checkout -- engine/src/core/Time.cpp`。
- **成本**：套件多约 35ms（当前全集 0.13s，可忽略）。
- **状态（2026-09-28）：✅ 已关闭 —— 而且是本项目第一条"先设计、再反向验证"的守卫**。

### B4 修文档里那句**没有依据**的话（"float 累加会漂成 59.94"）

- **现状**：这句话出现在 4 处：
  `engine/src/core/Time.cpp:67-68`（代码注释）、`doc/S3_CHECKLIST.md:555`（伪代码注）、
  `:677`（坑表第 4 条）、`:818`（反向验证 1 的预期结果）。
- **为什么站不住**：
  1. `LimitFPS()` 每帧都以**当帧的 `m_begin`** 重新计算 `elapsed`，`BeginFrame()` 每帧重置
     基准 —— 所以 `target` 的浮点误差**不可能跨帧累积**，压根没有"漂移"的机制。
  2. 量级也对不上：`1.0f/60.0f` 在 float 里的误差约 **1 纳秒/帧**，
     60 帧累计 60ns，顶栏那一格是 0.1ms —— 差 1000 倍，肉眼永远看不见。
  3. **`59.94` 是 NTSC 的 1000/1001 系数**，和浮点累加没关系。原句是把一个熟悉
     数字安到了一个不相关的原因上。
- **真实的陷阱是什么**：**毫秒截断**。若把目标帧时间写成
  `duration_cast<milliseconds>(1/60 秒)` 会得到 **16ms**（而不是 16.667ms）→
  顶栏会稳定停在 **~62**（不是 60.0，也不是"漂移"）。这才是一条能一眼看出来的错。
  计算：16ms 的倒数是 62.5，再减去实际等待开销 → 顶栏读 ~62。
- **处置**：
  1. 4 处文字改成上面的准确说法（整数纳秒的收益是**避免毫秒截断 + 可复现**，
     不是"防漂移"）
  2. `doc/S3_CHECKLIST.md` 10.3 反向验证 1 **改写成可验证的形式**：
     把目标帧时间改成 `milliseconds(1000/60)`，期望看到顶栏稳定在 ~62（而不是漂移）

- **验收**：文档里搜 `59.94` 应只剩"这个说法是错的"这一段本身。

> · `Application.cpp` 里那个"最小可用尺寸"常量 `2` 是**两处共用**的，但两处行为**不同**：

### 4.2 关于 C10（ConPTY 的 key-up）—— 证据、两条修法、为什么先跳过

**证据（2026-09-30 本人实测，数字与预测完全吻合）**

| 场景 | 预测（若"每次按键 = 恰好一帧"） | 实测 |
| --- | --- | --- |
| `MiniEngine.exe 60 30` 轻点一次 `D` | `pos.x = 2.50 + 30×(1/60) = ` **3.00** | **3.0** |
| `MiniEngine.exe 240 30` 轻点一次 `D` | `pos.x = 2.50 + 30×(1/240) ≈ ` **2.625** | **2.6 左右** |

推论：**每次按键被恰好折算成一帧的 `dt`** → ConPTY 把每个按键合成为"down + 立刻 up"，
所以 `Get()` 永远是 `Pressed`、**永远不会是 `Held`**。按住的位移 = `自动重复速率 × 一帧的 dt`，
只有 `v × 真实时间` 的 `1/2`（60fps）到 `1/8`（240fps）。

**为什么 S3 没暴露**：S3 用的是 `Get() == Pressed`（边沿触发），而"合成对"恰好产出一个 `Pressed`
—— 坏掉的输入与旧语义**正好吻合**。S5 换成 `IsDown`（电平）才把它露出来。

**修法 A（首选，成本 2 行）**：启动时向 stdout 写 Win32 Input Mode 的开启序列 `\x1b[?9001h`，
退出时**必须**写 `\x1b[?9001l`（不关会污染退出后的 shell —— 与"备用屏没恢复"同类）。
启用后终端改发 `CSI Vk;Sc;Uc;Kd;Cs;Rc _`，ConPTY 把它转成**正确的** `KEY_EVENT_RECORD`
（`bKeyDown` 真正表示按下/抬起）。`InputWindows` **不用改**（它本来就按 `bKeyDown` 分流）。
⚠️ 四个必须先实测的未知点：① 老 conhost / 老 Windows Terminal 不支持该序列（应被忽略、无害，
但那样 ConPTY 下仍然不可玩）；② 经典控制台下加这句有没有副作用；③ 是否还需要
`ENABLE_VIRTUAL_TERMINAL_INPUT`；④ ConPTY 会不会把这条序列本身当成一条输入记录喂回 `Poll()`。

**修法 B（回退，成本 ~30 行 + 测试）**：在 `InputState` 里做"**按自动重复推断按住**" ——
连续收到同一个键的 `OnKeyDown`（自动重复）就认为它仍被按住，超过"N 倍重复间隔"没新事件才算抬起。
好处：不依赖终端配合，且**移动仍是 `v × dt`**（推断的是"按键状态"，不是"位移"），
不会破坏 dt 无关性。代价：`InputState` 需要知道时间（现在它是纯逻辑、不读时钟，要改成接收 `dt`），
而且要选一个超时参数（`< 自动重复间隔` 会误判抬起，`>` 会让松开后多走一会）。

**为什么先跳过（本人决定）**：S5 的**交付物本身成立** —— "速度 × dt"这条链在测试里是可证的
（`World.MovementIsDtIndependent` + `Game` 三个用例都过），ConPTY 限制的是**输入能提供什么信息**，
不是我们的积分模型。代价是：**在 VS Code 终端里 S5 的"按住"手感不可用**，
且 10.2 那条自证 `pos ≈ v × sum dt` **只在提供真 key-up 的终端里成立**（已在 `S5_CHECKLIST` 标注）。

### 4.3 关于 C11（`Camera::ScreenToWorld` 只有契约）

**现状**：`engine/include/mini/render/Camera.h` 里以**注释**形式写了契约 ——
`ScreenToWorld(col, row) = camera.pos + {col + 0.5, row + 0.5}`，拿到的是那一格的**中心**；
**没有实现**（S6 全程 0 个调用者）。

**为什么算债**：头注释里的公式也是承诺。S9 真用它的时候，最省事的写法是
`pos + {col, row}` —— **差半格**，而症状正是 E-8 那一类"偏移半格 / 走位比视觉慢一格"。
把"必须是格中心"这件事留在注释里、没有用例守着，等于把半格偏移的坑留给未来的自己。

**触发条件**：任何"屏幕坐标 → 世界坐标"的需求 —— S9 的瞄准 / 鼠标拾取 / 子弹落点换算。

**做的时候注意**：
① 必须用**浮点的 `camera.pos`**，不能用整数原点（`OriginCol/OriginRow`）——那会丢掉小数部分；
② 用例要钉往返：`ToIndex(ScreenToWorld(col, row))` 与该列/行对应的世界格一致；
③ 与 `Camera` suite 的用例 11（实体与 tile 必须同列）是同一个坐标系下的两条边。

### 4.4 关于 C12 / C13（S7 的两条"不做"）—— 为什么当场砍掉

两条都是 `PLAN` 的 S7 小节里**写了、但本阶段没做**的目标。按 B2 / C11 / S4 差异 2 的既定纪律
（"**0 调用者不建**"），当时判掉：

**C12 实体间 AABB 推挤**（`PLAN:544`）
- **现状**：世界里只有 **1 个实体会动**（玩家）。`World` 里没有第二个实体会动，也没有任何代码需要
  "两个实体不能重叠"这条语义。
- **为什么算债**：不算"欠着的功能"，算"**当时判掉、需要写清触发条件**"。
  如果不写触发条件，它会从"有意推迟"变成"真忘了"——而那正是本节存在的意义。
- **触发条件（2026-10-09 S8 收口时改写）**：~~S8 出现第二个会动的实体~~ → **S10 刷怪之后**。
  ⚠️ **S8 确实出现了第二个会动的实体（5 个敌人），但仍然不做**，理由有二：
  ① S8 的验收项是"5 个敌人同时追不出现抖动打转"，而**抖动来自状态阈值抖动，不是重叠** ——
     治法是迟滞（`sight < lose`），推挤治不了它；
  ② 做推挤要改 `World::Update`（两趟循环），而**玩家会被敌人推走** → `Game` suite 那 4 条
     既有用例的期望值全部作废（正是 S7 偏差 7"接线后既有用例真红"的重演）。
  于是代价被明确接受：**敌人之间会互相重叠、直接穿过彼此**（人眼验收里按"预期行为"记，不算失败）。
  真正需要它的时刻是 **S10 刷怪**（同屏敌人变多、叠成一坨影响可玩性）。
- **届时做法**：把 `World::Update` 的循环改成两趟（先全部积分 + 撞墙，再解算实体间重叠），
  并且**必须避开 E-9（迭代器失效）**：推挤不许在遍历中改容器。
  ⚠️ 还要**同时改 `game/` 的敌人循环**（`DriveEnemyAi`）—— 它现在假设"只有自己在动别人"。
- **注意**：`Collision.h` 现在**没有**任何"实体列表"参数 —— 这是有意的（它不认识 `EntityId`）。
  加推挤时**不要**把实体列表塞进 `Collision.h`，而是新写一个函数，让 `World` 负责"先移动后推挤"的顺序。

**C13 F2 显示"碰撞盒"**（`PLAN:549`）
- **现状**：项目**没有** Debug Overlay；`Key::F2` 在 `KeyCode.h:31,83` 里已有 VK 映射，
  注释写着"S11 的 Debug Overlay 用" —— 但**0 个调用者**。
- **为什么算债**：同上，是"有触发条件的推迟"。而且**在 1 格 = 1 字符的终端里**，
  "显示碰撞盒"最多只能做到"把角色占据的那一格换个颜色"：盒宽恰好 1 格，
  与"角色自己画的那一格"**完全重合**，信息量接近 0。
- **触发条件**：**S11**（Debug Overlay）。届时更值得画的是"哪些格是实心 + 实体占了哪些格"，
  而不是"盒的边框"（后者在字符分辨率下没有可画的东西）。
